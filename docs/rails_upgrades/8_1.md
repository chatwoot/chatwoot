# Production migration guide: Rails 8.1.4.1

This checkpoint upgrades Chatwoot from Rails 8.0.5.2 to Rails 8.1.4.1. It deliberately keeps `config.load_defaults 7.0`, the existing Sidekiq/Redis architecture, and all persisted serializer and encryption settings from the preceding checkpoints.

Deploy and observe the Rails 8.0.5.2 checkpoint before this release. There is no database migration or data rewrite in the Rails 8.1 checkpoint.

## Application-level changes

- Rails and every Rails component move from 8.0.5.2 to 8.1.4.1.
- `acts-as-taggable-on` moves to 13.0.0 because version 12 excludes Active Record 8.1.
- `devise-two-factor` moves to 6.4.1 and `devise_token_auth` to 1.3.0 because their previous releases exclude Rails 8.1. `devise_token_auth` 1.3.0 disables Devise's wrapper email dirty check, so `User` delegates that check to Active Record to preserve email reconfirmation.
- Bullet moves to 8.3.1 because 8.0.7 does not recognize Active Record 8.1.
- `omniauth-rails_csrf_protection` moves to 2.0.1, removing its use of the Rails-8.1-deprecated `ActiveSupport::Configurable` interface without changing Chatwoot's OmniAuth routes.
- Rails 8.1 always makes `to_time` preserve the receiver's timezone. The now-deprecated transition setting is removed; winter and daylight-saving offsets are checked by the production preflight.
- The schema dump uses `ActiveRecord::Schema[8.1]`. The schema version is unchanged and there are no migrations in this checkpoint.
- Rails 8.1 removes its built-in Azure Active Storage service. Chatwoot already moved to the external `azure-blob` adapter in the Rails 7.2 checkpoint, and the `microsoft` service name and persisted blob service names remain unchanged.
- Sidekiq remains on 7.3.10. The preflight proves that Active Job loads the adapter shipped by Sidekiq rather than Rails' deprecated built-in adapter.
- The Rails 8.0 route replacement remains intact. The `app_account_path` and `app_account_conversation_path` helpers are unchanged.

## Breaking request behavior to audit

Rails 8.1 removes two deprecated query-string behaviors:

- A leading bracket is retained in a parameter name. For example, `[filter]=open` no longer becomes `filter=open`.
- A semicolon is no longer a query-string separator. For example, `status=open;page=2` is one `status` value rather than two parameters.

Chatwoot has no application code that depends on either behavior, but an old API client, OAuth provider, or webhook sender could still send such a query. Before deployment, sample ingress logs for leading-bracket parameter names and semicolon-separated queries. Migrate an affected client to normal percent-encoded `key=value&key2=value2` syntax before the canary.

Rails 8.1 also serializes a `nil` query value as a bare key (`token`) instead of an empty assignment (`token=`). Chatwoot's confirmation flow supplies a real token, so the product URL is unchanged. The mailer specs now use the token generated by Devise rather than depending on the old rendering of `nil`.

Rails 8.1.4.1 also rejects conflicting client addresses in `Forwarded` and `X-Forwarded-For` when IP spoofing checks are enabled. Verify that the staging ingress strips untrusted forwarding headers and sends consistent client addresses. See the [Rails RemoteIp advisory](https://github.com/rails/rails/security/advisories/GHSA-2gff-2mmg-m73p).

## Before deployment

1. Confirm the production release being replaced is the Rails 8.0.5.2 checkpoint and its observation window is complete.
2. Take the normal PostgreSQL and Redis backups and verify the database backup can be restored.
3. Build with Ruby 3.4.4, Node 24, and the locked Bundler and pnpm versions.
4. Build both Vite and Sprockets assets in production mode.
5. Run the read-only preflight against a production replica or during the maintenance window:

   ```sh
   RAILS_ENV=production \
   EXPECTED_RAILS_VERSION=8.1.4.1 \
   EXPECTED_CONFIG_DEFAULTS=7.0 \
   EXPECTED_SIDEKIQ_VERSION=7.3.10 \
   EXPECTED_AZURE_SERVICE=AzureBlob \
   bundle exec rails runner script/rails_upgrade/preflight.rb
   ```

   Leave `PREFLIGHT_MAX_ENCRYPTED_ROWS` unset or set it to `0` for the release preflight so every encrypted value is read. A non-zero value is only a bounded rehearsal.

6. Run the Active Storage write/read/delete smoke against every configured service:

   ```sh
   RAILS_UPGRADE_ALLOW_STORAGE_WRITE=true \
   RAILS_UPGRADE_STORAGE_SERVICE=<service-name> \
   bundle exec rails runner script/rails_upgrade/active_storage_smoke.rb
   ```

7. For an installation using `ACTIVE_STORAGE_SERVICE=microsoft`, require the smoke output to report `ActiveStorage::Service::AzureBlobService`. Test against the real staging Azure account, not only an emulator.
8. Exercise password login, API-token validation, OmniAuth, MFA enrollment/login/recovery, and Super Admin login with the production encryption configuration.
9. Compare the Rails 8.0 and Rails 8.1 route tables. URL helpers, verbs, paths, and controllers must remain identical.

## Database rehearsal

There is no migration to run. The `db/schema.rb` diff updates the schema dumper version and normalizes extension and index declarations.

```sh
RAILS_ENV=production bundle exec rails db:abort_if_pending_migrations
RAILS_ENV=production SCHEMA=/tmp/chatwoot-rails-8-1-schema.rb bundle exec rails db:schema:dump
```

On a disposable database, load the Rails 8.1 schema and compare tables, columns, types, nullability, defaults, indexes, constraints, extensions, foreign keys, and triggers with a database loaded by Rails 8.0. Never run `db:schema:load` against an existing production database.

## Deployment order

1. Build and publish the image only after Vite and Sprockets production builds succeed.
2. Run `bundle exec rails db:abort_if_pending_migrations`; no Rails 8.1 migration should be pending.
3. Start one Rails web canary.
4. Verify health, agent login, API authentication, MFA, OmniAuth, the dashboard, conversation rendering, query/filter endpoints, attachment access, Action Cable, and Super Admin pages.
5. Replace the remaining web processes.
6. Start one Sidekiq canary and verify immediate, scheduled, retry, mail, webhook, and cron jobs.
7. Wait for at least one minute-level cron job to enqueue and complete, then replace the remaining workers.
8. Run the production preflight again against the primary database.

Rails 8.0.5.2 and 8.1.4.1 processes may overlap during a rolling deployment because this checkpoint has no schema change and retains Rails 7.0 framework defaults and persisted formats.

## Post-deployment checks

- `Rails.version` reports `8.1.4.1`, and the preflight reports framework defaults `7.0`.
- The preflight reports that winter and daylight-saving `to_time` offsets are preserved.
- Agent, Super Admin, API-token, OmniAuth, and MFA authentication remain successful.
- Label and tag assignment still produce the same stored values and API payloads.
- Reporting totals and time buckets match Rails 8.0 in UTC and at least one daylight-saving account timezone.
- Existing and new attachments read and write successfully on every configured storage backend.
- The minute-level IMAP cron entry is enqueued and performed by a Rails 8.1 Sidekiq worker.
- No increase occurs in decrypt errors, login failures, HTTP 4xx/5xx responses, Sidekiq retries, dead jobs, webhook failures, mail failures, or Active Storage errors.

## Known follow-up deprecations

- Devise 4.9.4 still calls the Rails routing `resource` DSL with a positional options hash. Rails 8.1 accepts it and warns that Rails 8.2 will require keywords. `devise-secure_password` 2.2.1 still constrains Devise below 5, so resolve that upstream dependency chain before Rails 8.2 rather than monkey-patching this checkpoint.
- Rack 3.2's `:unprocessable_entity` warning remains a separate cleanup; Rails 8.1 still maps it to HTTP 422.
- The existing RubyLLM legacy API and MiniMagick/Ruby `benchmark` warnings are unrelated to this Rails checkpoint and should remain separate dependency work.

## Rollback

Rollback is code-only:

1. Restore the Rails 8.0.5.2 web and worker release.
2. Keep PostgreSQL, Redis, Active Storage, and queued-job data created during the canary; their formats are unchanged.
3. Re-run login, MFA, OmniAuth, attachment, reporting, Super Admin, and representative immediate/scheduled job checks.
4. Run the Rails 8.0 preflight with `EXPECTED_RAILS_VERSION=8.0.5.2`.

Do not activate Rails 8.0 or 8.1 framework defaults in this rollout. Defaults, serializer formats, encryption behavior, and the HTTP 422 symbol cleanup remain separately deployable work.
