# Production migration guide: Rails 8.0.5

This checkpoint upgrades Chatwoot from Rails 7.2.3.1 to Rails 8.0.5. It deliberately keeps `config.load_defaults 7.0`, the existing Sidekiq/Redis architecture, and every persisted serializer and encryption setting from the Rails 7.2 release.

Deploy and observe the Rails 7.2.3.1 checkpoint before this release. There is no database schema or data migration in the Rails 8.0 checkpoint.

## Application-level changes

- All 39 remaining keyword-form enum declarations in 31 OSS and Enterprise model files use Rails 8's positional declaration API. The enum names, integer mappings, scopes, and stored values do not change.
- The mailer conversation route is expressed as a named `scope`, because Rails 8 rejects `index` on a singular `resource`. The `app_account_conversation` helper, controller, verb, and `/app/accounts/:account_id/conversations/:id` path are unchanged.
- `config.action_dispatch.show_exceptions` uses the symbolic `:all` mode in test, replacing the deprecated boolean form without changing test response behavior.
- `ActiveSupport#to_time` opts into the Rails 8.1 `:zone` behavior now. Reporting and timezone-boundary specs pass with this behavior before the Rails 8.1 runtime upgrade.
- Groupdate moves to 6.8.0. Older Groupdate releases patch Active Record calculation internals that Rails 8 removed and can silently return zero totals or fail reporting queries.
- Administrate moves to 1.0.0 and `administrate-field-active_storage` to 1.0.6. Chatwoot owns Sprockets explicitly and uses Administrate's prebuilt stylesheet.
- The Rails-8-incompatible `administrate-field-belongs_to_search` gem is removed. A local field preserves its remote JSON search behavior, so the account-user form does not load every account and user into HTML.
- Audited moves to 5.8.0, Hairtrigger to 1.3.1, Rails I18n to 8.0.2, and Sprockets Rails to 3.5.x.
- `ActionController::ParameterMissing` now renders “empty or invalid” in its exception message. The exception class and `param` value are unchanged.
- Rails 8 adds `params.expect`, but the existing `require(...).permit(...)` API remains supported. The new RuboCop migration rule is disabled for this checkpoint because mechanically changing every controller would alter malformed-request rejection semantics; migrate that interface separately with request-contract coverage.

## Before deployment

1. Confirm the production release being replaced is the Rails 7.2.3.1 checkpoint and that its observation window is complete.
2. Take the normal PostgreSQL and Redis backups and verify the database backup can be restored.
3. Build with Ruby 3.4.4, Node 24, and the locked Bundler/pnpm versions.
4. Build both Vite and Sprockets assets in production mode.
5. Run the read-only preflight against a production replica or during the maintenance window:

   ```sh
   EXPECTED_RAILS_VERSION=8.0.5 \
   EXPECTED_CONFIG_DEFAULTS=7.0 \
   EXPECTED_SIDEKIQ_VERSION=7.3.10 \
   EXPECTED_AZURE_SERVICE=AzureBlob \
   bundle exec rails runner script/rails_upgrade/preflight.rb
   ```

6. Run the Active Storage write/read/delete smoke against every configured service:

   ```sh
   RAILS_UPGRADE_ALLOW_STORAGE_WRITE=true \
   RAILS_UPGRADE_STORAGE_SERVICE=<service-name> \
   bundle exec rails runner script/rails_upgrade/active_storage_smoke.rb
   ```

7. On a production-sized staging database, open Super Admin → Account Users → New. Search for an account and user while watching the browser network panel. Each lookup must call the corresponding `/super_admin/*.json?search=` endpoint and must not embed the complete table in the initial HTML.

## Database rehearsal

No migration is added, but rehearse both database entry paths:

```sh
RAILS_ENV=production bundle exec rails db:abort_if_pending_migrations
RAILS_ENV=production SCHEMA=/tmp/chatwoot-rails-8-schema.rb bundle exec rails db:schema:dump
```

For a disposable database, load the checked-in schema, run the preflight, and compare the dumped tables, extensions, indexes, foreign keys, and triggers with the Rails 7.2 dump. The custom PostgreSQL schema dumper remains compatible with Rails 8.0 and continues to omit only the explicitly configured experimental extensions.

## Deployment order

1. Build and publish the image only after Vite and Sprockets production builds succeed.
2. Run `bundle exec rails db:abort_if_pending_migrations`.
3. Start one Rails web canary.
4. Verify health, agent login, API authentication, the dashboard, conversation rendering, attachment access, Action Cable, Super Admin pages, and remote Account User searches.
5. Replace the remaining web processes.
6. Start one Sidekiq canary and verify immediate, scheduled, retry, mail, webhook, and cron jobs.
7. Wait for at least one minute-level cron job to enqueue and complete, then replace the remaining workers.
8. Run the production preflight again against the primary database.

Rails 7.2.3.1 and 8.0.5 processes may overlap during a rolling deploy because this checkpoint has no schema change and keeps Rails 7.0 framework defaults and persisted formats.

## Post-deployment checks

- `Rails.version` reports `8.0.5`, and the preflight reports framework defaults `7.0`.
- Reporting totals and time buckets match the Rails 7.2 release in UTC and at least one non-UTC account timezone.
- Super Admin pages load their JavaScript and CSS, and Account User remote selects return only matching records.
- Existing and new attachments read and write successfully on every configured storage backend.
- No increase occurs in decrypt errors, login failures, HTTP 5xx responses, Sidekiq retries, dead jobs, webhook failures, or mail failures.
- The `app_account_conversation` route continues to generate `/app/accounts/:account_id/conversations/:id`.

Rack 3.2 warns that the `:unprocessable_entity` symbol will eventually become `:unprocessable_content`. Both map to HTTP 422, and Rails 8.0/8.1 continue to support the existing symbol. Chatwoot has 112 application/spec files using the old name; migrate those in a separate mechanical change to avoid obscuring this framework checkpoint.

## Rollback

Rollback is code-only:

1. Restore the Rails 7.2.3.1 web and worker release.
2. Keep the PostgreSQL, Redis, Active Storage, and queued-job data created during the canary; their formats are unchanged.
3. Re-run login, attachment, reporting, Super Admin, and representative immediate/scheduled job checks.
4. Run the Rails 7.2 preflight with `EXPECTED_RAILS_VERSION=7.2.3.1`.

Do not activate Rails 8.0 framework defaults in this rollout. Defaults, serializer formats, encryption behavior, and the HTTP 422 symbol cleanup remain separately deployable work.
